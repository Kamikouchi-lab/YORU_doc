YORU is growing into a family of programs. YORU itself detects animal behaviours. Sister applications such as YORU Tracker build on YORU's detectors for work of their own, and trigger plugins act on what YORU detects while an experiment runs. This page shows how the parts fit together. New parts are added to it as they appear.

Rules that hold the family together

Sister→YORU
YORU✕Sister

One-way dependency

Sister applications depend on YORU. YORU never imports one, and its windows contain nothing that belongs to one.

detectors OBB camera GUI

Share building blocks, not screens

A sister application builds its own windows from YORU's GUI primitives. It does not subclass or copy YORU's screens.

external API = promise

The external API is a promise

Changing one of its names breaks every sister application. Such a change needs a new major version of YORU, or a deprecation period. YORU's tests pin every name.

~/.yoru/logs/
yoru.log yoru_tracker.log

One place for logs

Each program writes its own log file into YORU's log folder, so a problem report needs only one folder.

Where does a new feature go?

Ask these questions in order. The first yes decides.

  1. Is it about which animal is which: identities, trajectories, or state carried across many frames?

    yes YORU Tracker

  2. Does it act on a detection during an experiment, for example by switching hardware or showing a stimulus?

    yes A trigger plugin

  3. Does YORU need it to detect behaviours or run closed-loop experiments?

    yes YORU

  4. Is it a general building block (a detector, an oriented-box, camera or GUI utility) that more than one application needs?

    yes YORU's external API

  5. Is it optional, expensive or model-heavy, with a workflow of its own?

    yes A sister application

A feature never goes into YORU only because a sister application could use it there. YORU keeps general, stable building blocks. Tracking logic, identity logic and tracking screens stay in YORU Tracker.
